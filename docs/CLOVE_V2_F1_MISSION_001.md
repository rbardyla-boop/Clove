# CloveLearn v2 — F1 Mission 001

Status: **SPECIFICATION ONLY / NON-PRODUCTION**  
Branch: `f0/brotherhood-salvage-audit-2026-08-12`  
Target population: **men aged 18–24**  
Program concept: **Brotherhood Without an Enemy**  
Mission: **MAKE YOURSELF USEFUL**

## F1 claim

> A first-time CloveLearn user can choose one bounded real-world mission, leave the site, complete a verifiable action for himself or another person, return, record what actually happened, and finish with a next step rather than another content recommendation.

This is a product-mechanism claim, not a mental-health or wellbeing claim.

F1 does **not** claim that one mission reduces loneliness, treats depression, creates brotherhood, increases masculinity, prevents radicalization, or produces lasting purpose.

## Success condition

F1 passes only if the path is understandable and executable without requiring a social feed, mentor marketplace, AI companion, rank system, payment, account, or external community integration.

The core loop is:

`ARRIVE → CHOOSE → COMMIT → DO OFFLINE → RETURN → EVIDENCE → DEBRIEF → NEXT`

The website must not become the activity. The real-world action is the activity.

---

# 1. Entry proposition

Primary line:

> **MAKE YOURSELF USEFUL.**

Supporting line:

> Pick one thing that leaves the world slightly better because you showed up.

No masculinity lecture. No diagnosis. No ideology. No promise that the user will feel better afterward.

The user chooses one of four mission classes.

---

# 2. Mission classes

## 2.1 FIX

Repair, restore, maintain, diagnose, or improve a real physical thing.

Examples:

- repair a bicycle;
- fix a loose hinge, drawer, lamp, appliance, fence, tool, or piece of furniture;
- sharpen or service a tool;
- diagnose why something does not work;
- restore an item instead of replacing it.

Completion rule:

A FIX mission completes when the user records:

1. what was wrong;
2. what action was attempted;
3. the observable result;
4. whether the item is now functional, improved, unchanged, or worse;
5. one thing learned.

A failed repair is still a completed mission if the attempt and result are honestly documented.

## 2.2 SERVE

Perform a bounded action that is useful to another person, household, community, or organization.

Examples:

- help someone move, carry, clean, organize, shovel, mow, prepare, or repair;
- volunteer for a real task;
- prepare food for someone;
- help an older or disabled person with a practical task they actually want done;
- collect litter from a defined public area where doing so is lawful and safe.

Completion rule:

A SERVE mission completes when the user records:

1. who or what was served using a non-identifying category if desired;
2. what was actually done;
3. approximately how long it took;
4. what observable result existed afterward;
5. whether the action was wanted/useful rather than imposed.

No points are awarded for savior narratives, unsolicited intrusion, or posting another person's vulnerability.

## 2.3 LEARN

Acquire and demonstrate one concrete skill or sub-skill.

Examples:

- tie a specific knot correctly;
- change a tire;
- use a multimeter for one bounded diagnostic task;
- cook one basic meal from scratch;
- perform a basic first-aid skill using an approved training source;
- learn a tool, trade, outdoor, repair, communication, or practical household skill.

Completion rule:

A LEARN mission completes when the user can demonstrate the skill against a stated check rather than merely consume instructional content.

`watched/read` is not completion.

`can now do X` is completion.

## 2.4 BUILD

Create a physical or digital artifact that another person could actually use.

Examples:

- simple shelf, stool, planter, storage solution, repair jig, template, checklist, small software utility, map, guide, or community resource;
- improve an existing object or process rather than creating novelty for its own sake.

Completion rule:

A BUILD mission completes when there is an artifact with a stated intended user or use and a brief test of whether it works for that purpose.

---

# 3. Mission selection rules

The first mission should normally be:

- completable within **15 minutes to 4 hours**;
- low-cost or no-cost;
- legal;
- physically appropriate for the user's competence and condition;
- specific enough to know when it is finished;
- not dependent on another person responding online;
- not primarily content consumption;
- not performed for likes, views, status, or public validation.

The user may reject suggested missions without penalty.

Clove should prefer a smaller completed action over an impressive abandoned one.

---

# 4. Commitment contract

Before leaving Clove, the user records only:

- mission class;
- exact action;
- expected completion check;
- expected duration;
- first physical action;
- optional intended start time.

Example:

```text
CLASS: FIX
MISSION: Get the old bicycle shifting reliably enough for a test ride.
DONE WHEN: All gears can be selected without the chain dropping.
EXPECTED: 90 minutes.
FIRST ACTION: Put the bike in the stand and inspect cable tension.
```

The commitment page then says:

> **Close Clove. Go do it.**

No endless recommendations appear below this line.

---

# 5. No-content escape hatch

If the user is stuck before beginning, Clove may expose a single salvaged Micro Ops function:

> **WHAT IS THE NEXT PHYSICAL ACTION?**

It may break the mission into the next one to three actions.

It must not generate a new project, expand scope, or turn planning into the mission.

---

# 6. Return and evidence

On return the user selects:

- `DONE`
- `PARTLY DONE`
- `FAILED / DID NOT WORK`
- `DID NOT START`

None of these states deletes the mission or resets progress.

## 6.1 Evidence model

F1 does not require public proof.

Acceptable private completion evidence can be:

- concise text describing the observable result;
- before/after state recorded locally;
- optional photo chosen by the user;
- optional external verification where naturally available.

A photo is never mandatory.

No face, address, geolocation, workplace identifier, child, client, patient, or vulnerable person's identity should be requested for mission verification.

Clove verifies **specificity**, not truth by surveillance.

The system should say:

> This is your record. If you lie to it, the number becomes meaningless.

---

# 7. Debrief

Reuse the useful structure from the existing After-Action Review and Failure Autopsy rather than inventing another reflection system.

For `DONE` or `PARTLY DONE`:

1. What did you actually do?
2. What was different from the plan?
3. What was harder than expected?
4. What did you learn?
5. Did this action help anyone besides you? `yes / no / unsure`
6. What is the next useful action, if any?

For `FAILED / DID NOT WORK`:

1. What did you attempt?
2. Where did it fail?
3. Was the problem knowledge, tools, time, scope, fear/avoidance, another dependency, or something else?
4. What did the failure teach you?
5. `RETRY SMALLER / GET HELP / LEARN FIRST / ABANDON FOR A REASON`

For `DID NOT START`:

1. What stopped the first action?
2. Was the mission too large, unclear, unsafe, unwanted, dependent on someone else, or simply avoided?
3. Choose: `SHRINK / REPLACE / SCHEDULE / DROP`.

No shame language. No streak loss. No public failure marker.

---

# 8. Reintegration rule

Failure must lead back into participation.

A user who fails is not placed below a user who succeeds.

The product may distinguish:

- mission attempted;
- mission completed;
- lesson recorded;
- help requested;
- mission retried.

It must not create a public failure score.

This rule is foundational for Brotherhood Without an Enemy: correction without exile.

---

# 9. Safety boundary

Mission 001 must not suggest or encourage:

- illegal activity;
- confrontation, vigilantism, or "testing" strangers;
- weapons use;
- hazardous electrical, gas, structural, medical, automotive, height, confined-space, chemical, or power-tool work beyond the user's demonstrated competence;
- trespassing;
- entering another person's home/property without permission;
- unsupervised activity involving minors;
- mental-health exposure exercises;
- deliberate sleep deprivation, fasting, substance use, pain, humiliation, or dangerous physical challenges;
- contacting an estranged person as a mission;
- public disclosure of another person's private information;
- "prove yourself" dares.

When uncertainty exists, the system should offer a lower-risk mission class rather than escalating risk.

F1 is for adults 18–24. Minors are outside scope.

# 12. F1 acceptance tests

## A. Ten-second comprehension

A new user can explain the page as:

> "I pick something real, go do it, then come back and record what happened."

If the explanation centers on self-help content, masculinity theory, AI, gamification, or social media, FAIL.

## B. Offline-action gate

The path must explicitly tell the user to leave/close Clove before execution.

If the nominal mission can be completed entirely by clicking through Clove, FAIL.

## C. Completion determinacy

Every suggested mission must have an observable completion check.

If "done" depends only on mood or motivation, FAIL.

## D. Failure survival

`FAILED` and `DID NOT START` must both produce a legitimate next state without deleting progress or shaming the user.

If failure traps or ejects the user, FAIL.

## E. Privacy

Mission completion cannot require public posting, identity disclosure, precise location, contact upload, or photo proof.

Any mandatory social proof is FAIL.

## F. Safety

A deliberate unsafe mission fixture must be rejected or redirected to a lower-risk alternative.

If dangerous work is framed as courage or character-building, FAIL.

## G. No-engagement trap

After commitment, the interface cannot present an infinite feed or recommendations designed to keep the user on-site.

If Clove competes with mission execution for attention, FAIL.

---

# 13. Terminal states

## PASS

The specification and later implementation demonstrate an understandable, bounded, privacy-preserving `choose → do → return → evidence → debrief` loop, including safe failure/reintegration, with no social-system dependency.

## REPAIR_REQUIRED

Any acceptance test fails, mission completion is ambiguous, the system rewards browsing over doing, or safety/privacy requirements are unresolved.

## RETIRE

If real-user testing shows that the mission framing itself does not cause voluntary real-world action at a useful rate, do not rescue it with social/gamification complexity. Revisit the core proposition.
